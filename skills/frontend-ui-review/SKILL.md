# 프런트엔드 UI 구현 및 리뷰

## 범위와 라우팅

- 구현 요청이면 기존 구조와 스타일을 읽고 필요한 코드만 수정한 뒤 검증한다.
- 리뷰 요청이면 파일을 변경하지 않고 사용자 영향이 큰 결함부터 보고한다.
- JSP/JSTL은 [references/jsp.md](references/jsp.md), Vue는 [references/vue.md](references/vue.md), React는 [references/react.md](references/react.md)를 읽는다.
- CSS 또는 화면 품질이 범위에 포함되면 [references/css-ui.md](references/css-ui.md)를 읽는다.
- 여러 기술이 함께 있으면 실제 변경 대상에 해당하는 문서만 조합한다.

## 공통 작업 흐름

1. 프로젝트 지침, 프레임워크 버전, 빌드 명령, 기존 컴포넌트·디자인 토큰·상태 관리·테스트 관례를 확인한다.
2. 변경되는 사용자 흐름과 초기, loading, empty, success, error, validation, disabled 상태를 식별한다.
3. 기존 컴포넌트와 스타일을 우선 재사용하고 새 의존성이나 전역 상태, 추상화는 필요한 경우에만 추가한다.
4. 아래 공통 위험과 선택한 프레임워크 참고 문서를 기준으로 구현하거나 리뷰한다.
5. 가장 좁은 lint, type-check, 단위·컴포넌트 테스트를 실행한다. UI가 실행 가능하면 실제 브라우저에서 핵심 흐름과 대표 desktop/mobile viewport를 확인한다.

## 공통 필수 점검

- 상태와 이벤트의 소유자가 명확하고 같은 값을 여러 위치에 중복 저장하지 않는지 확인한다.
- API 응답 순서 역전, 중복 제출, 컴포넌트 해제 후 갱신, 요청 실패와 optimistic update 원복을 확인한다.
- 신뢰할 수 없는 값은 출력 문맥에 맞게 인코딩하고 raw HTML 렌더링은 명시적으로 정제된 콘텐츠에만 허용한다.
- 사용자가 결과를 이해할 수 있도록 loading, empty, error, validation, disabled 상태를 화면에 제공한다.
- 성능 최적화는 측정되거나 규모상 명백한 문제에 적용한다. 큰 목록, 중복 요청, 과도한 렌더링, 초기 bundle 증가를 우선 확인한다.

## 브라우저 검증

- 실행 가능한 UI 변경은 normal user input으로 최소 하나의 핵심 흐름을 확인한다.
- 초기 화면과 상호작용 후 상태를 각각 시각 점검하고 clipping, overflow, 겹침, 깨진 정렬, 읽기 어려운 텍스트가 없는지 확인한다.
- 프로젝트가 지원하는 대표 desktop/mobile 크기를 사용하고, 기준이 없으면 현실적인 큰 화면과 작은 화면을 하나씩 선택한다.
- console 오류와 실패한 네트워크 요청을 확인한다. 환경 제약으로 실행하지 못한 검증은 완료로 주장하지 말고 정확히 보고한다.

## 완료 보고

- 구현은 변경 내용, 변경 파일, 실행한 검증 명령과 결과, 브라우저 확인 범위, 남은 위험을 요약한다.
- 리뷰는 심각도 순서로 파일·라인, 사용자 영향, 수정 방향을 제시하고 파일을 변경하지 않았음을 밝힌다.
- 스타일 취향만으로 기존 관례를 뒤집거나 요청과 무관한 대규모 리팩터링을 제안하지 않는다.
