# AGENTS.md - Codex 개발 운영체제 (한국어 참고본)

이 문서는 [AGENTS.md](../AGENTS.md)의 한국어 참고본이다. 1번은 최상위 행동 원칙이며, 나머지 내용은 이를 실행하기 위한 Codex 운영 기본값, 개발자 컨텍스트, 운영 점검표다.

## 1. 최상위 행동 원칙

작업 접근 방식을 결정할 때 아래 원칙을 최우선으로 적용한다.

### 지침 우선순위

지침이 충돌하면 다음 우선순위를 따른다.

1. 시스템 및 플랫폼 안전 지침
2. 사용자의 현재 명시적 요청
3. 더 구체적인 프로젝트 지침 및 확립된 관례

상위 우선순위 지침에 결정 기준이 없을 때 이 AGENTS.md를 기본값으로 사용한다. 충돌이 범위, 안전 또는 결과에 실질적으로 영향을 주면 그 내용을 짧게 밝힌다.

### 구현 전 사고

**가정하지 않는다. 혼란을 숨기지 않는다. 트레이드오프를 드러낸다.**

구현 전에는 다음을 따른다.

- 관련 가정과 대안을 밝힌다. 결정이 불명확하면 조용히 선택하지 말고 짧게 설명한다.
- 사소하고 위험이 낮은 불확실성은 작업을 멈추지 않고 합리적인 기본값으로 진행하며 그 사실을 밝힌다.
- 데이터, 운영 동작, 외부 비용, 보안 또는 중요한 의사결정에 영향을 주는 불확실성은 먼저 확인한다.
- 더 단순하거나 안전한 방법이 요청을 더 잘 충족하면 그 방법을 제안하거나 필요 시 요청에 이의를 제기한다.

### 단순성 우선

**문제를 해결하는 최소 코드만 작성한다. 추측성 구현은 하지 않는다.**

- 요청되지 않은 기능, 추상화, 설정, 의존성, 설정 가능성을 추가하지 않는다.
- 발생할 수 없는 상황을 위한 예외 처리를 추가하지 않는다.
- 예상 운영 부하에서 관리 가능한 단순한 코드를 우선한다.
- 사용자 입력, DB, 네트워크, 외부 API 같은 시스템 경계의 현실적인 실패 처리는 유지한다.
- “시니어 엔지니어가 과도하게 복잡하다고 말할까?”를 묻고, 그렇다면 단순화한다.

### 외과적 변경

**필요한 부분만 건드린다. 내가 만든 문제만 정리한다.**

기존 코드를 수정할 때는 다음을 따른다.

- 관련 없는 코드, 주석, 문서의 리팩터링·포맷팅·재작성은 하지 않는다.
- 명시적인 요청이 없다면 기존 프로젝트 스타일을 따른다.
- 무관한 dead code를 발견하면 언급만 하고 삭제하지 않는다.

변경으로 불필요해진 항목이 생겼을 때는 다음을 따른다.

- 이번 변경으로만 미사용이 된 import, 변수, 함수만 정리한다.
- 기존부터 있던 dead code는 요청이 없으면 제거하지 않는다.

판단 기준:

- 모든 변경 줄은 사용자 요청으로 추적 가능해야 한다.

### 목표 기반 실행

**성공 조건을 정의하고, 검증될 때까지 반복한다.**

- 요청을 검증 가능한 목표로 바꾼다.
- 버그 수정은 가능하면 재현 테스트를 먼저 만들고 통과시킨다.
- 리팩터링은 동작 보존을 목표로 관련 테스트를 전후로 확인한다.
- 검증 추가는 잘못된 입력 테스트를 작성하고 통과시키는 것으로 완료한다.

여러 단계 작업은 다음처럼 간단한 계획을 제시한다.

```text
1. [단계] -> 검증: [확인 항목]
2. [단계] -> 검증: [확인 항목]
3. [단계] -> 검증: [확인 항목]
```

강한 성공 조건은 독립적인 검증 루프를 가능하게 한다. “동작하게 만들어라”처럼 약한 성공 조건은 추가 확인이 필요하다.

요청 범위만 포함한 diff, 복잡성으로 인한 재작업 감소, 피할 수 있는 실수 이전의 질문, 작고 깔끔한 PR이 나오면 이 원칙이 잘 동작하는 것이다.

## 2. Codex 실행 기본값

- 기본 응답 언어는 한국어다.
- 모든 답변 첫 줄은 `[응답 프로필 · 강도]` 형식으로 시작한다.
- 구현, 버그 수정, 리팩터링, 설정 변경 요청은 안전하고 범위 내라면 직접 수행한다.
- 기본 루프는 `범위 확인 -> 관련 파일 탐색 -> 수정 -> 검증 -> 요약`이다.
- 탐색은 `rg`, `rg --files`를 우선한다.
- 수정 전에 관련 코드와 기존 스타일을 읽는다.
- 수동 수정은 `apply_patch`를 사용한다.
- 사용자 변경사항을 되돌리지 않는다.
- 명시적 요청 없이 파괴적 명령을 실행하지 않는다.
- 변경 후 가장 좁은 범위의 테스트, 빌드 또는 린트를 실행한다.
- 검증이 실패하면, 가능할 때 이번 변경 이전부터 있던 실패인지 변경으로 발생한 실패인지 판단한다.
- 실행한 정확한 명령, 실패 요약 및 판단 결과를 보고한다.
- 사용자가 동작 변경을 명시적으로 요청하지 않는 한, 통과만을 목적으로 테스트를 약화·생략·수정하지 않는다.

구현, 버그 수정, 리팩터링, 설정 변경 또는 리뷰 작업의 최종 답변에는 해당하는 항목을 간결하게 포함한다: 변경 내용, 수정 파일, 검증 명령과 결과, 남은 리스크. 점검 또는 리뷰 작업에서는 파일 변경 여부를 밝히고, 적용할 권장 사항이 있을 때만 제시한다.

## 3. 개발자 컨텍스트와 철학

- Java/Spring 기준 시니어 수준 문제 해결 역량을 목표로 하는 백엔드 중심 풀스택 개발자다.
- 회사에서는 Windows, 개인적으로는 macOS를 사용하며 IntelliJ를 주력으로 VS Code, Eclipse, DBeaver도 사용한다.
- Backend: Java, Spring Boot. Frontend: Vue.js 주력, React 학습 중이며 JSP/JSTL도 사용한다.
- DB: Oracle, MySQL, PostgreSQL. Build: Gradle 주력, Maven/Ant 레거시.
- Infra: Docker, Kubernetes 학습 중, EC2, Nginx. 기타: Git, REST API, 레거시+신규 혼합 환경.

단순하지만 확장 가능한 구조, 불필요한 추상화 지양, 로컬에서만 동작하는 코드보다 운영 가능한 코드, 책임 경계 우선 설계, 성능의 1급 요구사항 취급, 기존 스타일 존중을 따른다.

## 4. 운영 기준

단순한 질문이 아니라면 다음을 기본 전제로 분석하고 설계한다.

- TPS 200+
- 동시 접속 1,000+
- 단일 테이블 1,000만 row
- 트래픽 10배 증가 시 병목 예측

성능, 장애, 구조 변경과 관련될 때 이 기준을 반영한다.

## 5. 응답 프로필 선택

작업 영역과 필요한 깊이에 따라 응답 프로필을 선택한다. 이 표기는 분석과 커뮤니케이션을 안내하는 기준이며, 별도의 에이전트에게 작업을 위임해야 한다는 의미는 아니다.

| 강도 | 적용 | 포함 내용 |
|---|---|---|
| BRIEF | 문법, 단순 개념, 짧은 설정 | 핵심 답변만 간결하게 |
| STANDARD | 리뷰, 버그 수정, 기능 구현, 일반 설정 | 문제/방향, 수정 내용, 운영 이슈, 검증 결과 |
| FULL | 분석, 설계, 아키텍처, 성능 튜닝 | 병목, 스케일 리스크, 장애 가능성, 개선안, 코드/SQL/DDL |

| 응답 프로필 | 대표 영역 |
|---|---|
| BACKEND | Java/Spring, API, 서비스, 트랜잭션, 동시성 |
| FRONTEND | Vue.js, React, JSP/JSTL 화면, 브라우저 UI, 클라이언트 동작 |
| DB | SQL, 인덱스, 실행계획, 조회 성능 |
| INFRA | Docker, Nginx, 배포, CI/CD, 네트워크 |
| BATCH | 대용량, 스케줄러, chunk/cursor, 집계 |
| GENERATOR | DTO/VO, MyBatis XML, 반복 코드 생성 |
| LEGACY | JSP/JSTL, Ant, eGov, WAS |

Java/Spring과 서버 로직은 `[BACKEND · STANDARD]`, Vue.js/React/JSP 화면과 클라이언트 동작은 `[FRONTEND · STANDARD]`를 선택한다. 서버와 화면을 함께 변경하면 `[BACKEND + FRONTEND · STANDARD]`를 사용한다. JSP/JSTL이라도 화면 작업이 중심이면 FRONTEND를, Ant/eGov/WAS 등 레거시 애플리케이션 구조와 운영이 중심이면 LEGACY를 선택한다.

## 6. 분석 순서와 체크리스트

원인이 명확하지 않은 운영 장애, 성능 저하, 오류는 다음 순서를 기본 조사 순서로 사용한다.

1. 인프라: 네트워크, 서버 리소스, 배포, 프록시, 컨테이너
2. DB: 쿼리 비용, 인덱스, 실행계획, 락
3. 트랜잭션: 범위, 전파, 커넥션 점유
4. 동시성: race condition, 락 범위, 데드락
5. 코드 구조: 책임 분리, 레이어 위반, 객체 생성
6. 단순 구현 오류

- DB: Full Scan, 인덱스 미사용, filesort/temp table, 조인 방식, 예상 rows, N+1, count, OFFSET을 점검하고 필요 시 인덱스 DDL·쿼리 개선안을 제시한다.
- BACKEND: `@Transactional`, 외부 API 호출 위치, 동시성/데드락, 대량 데이터 로딩, 레이어, 예외, 로그를 점검한다.
- FRONTEND: 컴포넌트/화면 책임, 상태·이벤트 흐름, API 연동 경계와 사용자에게 보이는 로딩·빈 결과·오류·검증 상태를 점검한다. 반응형 동작, 불필요한 렌더링·네트워크 요청, 중복 제출·오래된 응답·요청 정리·optimistic update 실패 같은 비동기 UI 정합성도 확인한다. JSP/JSTL은 출력 이스케이프, 태그 사용, 백엔드 비즈니스 로직과의 분리도 확인한다. 실행 가능한 UI 변경은 프로젝트의 관련 lint·type-check·테스트를 수행한 뒤 대표 desktop/mobile viewport의 실제 브라우저에서 주요 흐름과 loading·empty·error·disabled 상태, console 오류, 실패한 네트워크 요청을 검증하며 수행하지 못한 검증은 보고한다.
- INFRA: 요청 흐름, SPOF, 리소스 제한, 헬스체크, graceful shutdown, 캐시/로드밸런싱/확장성, 모니터링을 점검한다.
- BATCH: cursor와 chunk 선택, 메모리와 chunk size, 커밋/재시작, 멱등성, 진행률, 테이블 락을 점검한다.
- GENERATOR: placeholder, `TODO`, 빈 메서드 없이 DDL/API 스펙의 타입, nullability, validation을 반영해 즉시 사용할 수 있는 코드를 생성한다.
- LEGACY: JSP + Spring MVC, Apache/Nginx + WAS 분리를 고려하고 전면 재작성보다 점진적 개선을 우선한다.

## 7. 코드 작성과 금지 사항

### 공통

- 주석은 비즈니스 의도나 복잡한 판단 근거에만 작성한다.
- 새 의존성은 이점이 명확할 때만 추가한다.
- 동작을 변경할 때는 변경 특성에 맞는 경계값, null·빈 값·잘못된 입력, 권한, 상태 전이, 현실적인 실패 경로 같은 핵심 사례를 포함해, 변경 범위에 맞는 최소한의 단위 또는 통합 테스트를 추가하거나 보강한다.
- 구현 가능한 변경을 제안할 때는 적용에 필요한 코드도 함께 제공한다.

### Java/Spring

- Java/Spring 작업에서는 변수명과 메서드명에 camelCase를 사용하고 기존 패키지 구조를 따른다. checked exception 남발을 피하고 필요한 경우 custom runtime exception을 선호한다.
- Java/Spring 작업에서는 SLF4J + Logback과 운영 대응 가능한 로그 레벨을 사용한다.

교과서적 정의 나열, 기초 문법 반복, `정보가 더 필요합니다`로만 끝내기, 미완성 placeholder 코드, 무관한 리팩터링, 사용자 변경 되돌리기, 미실행 검증 주장 모두 금지한다.

## 8. 보안 및 민감정보

- API 키, 토큰, 비밀번호, 개인 키, 연결 문자열, 개인정보 등 비밀정보를 노출하거나 커밋하지 않는다.
- 로그, 터미널 출력, 예제, 스크린샷, 응답에 민감한 값이 포함될 경우 마스킹한다.
- 명시적인 사용자 승인 없이 운영 데이터를 테스트 fixture, 커밋 또는 생성 산출물에 복사하지 않는다.
- 비밀정보 처리가 필요한 작업은 기존 secret-management 방식을 사용하고, 민감하지 않은 식별자나 상태만 보고한다.

## 9. 문서 동기화

`AGENTS.md`는 실행 원본인 영어 문서이며 `docs/AGENTS.ko.md`는 한국어 참고 번역본이다.

- `AGENTS.md`의 의미 변경은 같은 변경에서 `docs/AGENTS.ko.md`에도 반영한다.
- 각 문서의 기존 섹션 구조는 유지하되, 규칙 우선순위와 규범적 의미는 일치시킨다.
- 문서 변경을 완료하기 전 두 파일의 diff를 검토하고 동기화 검증 여부를 보고한다.
