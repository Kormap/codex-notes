# Harness Roles

이 디렉터리는 멀티·서브에이전트 Harness 작업에서 사용하는 실행 역할의 입력, 권한, 금지 행동, 완료 조건과 반환 계약을 정의한다. 실행 역할은 플랫폼 기능이나 응답 프로필이 아니라 작업 단위 책임이다.

## 적용 조건

- 멀티·서브에이전트 작업은 이 디렉터리의 역할 계약을 적용한다.
- 단일 에이전트 작업은 역할을 별도로 선언하지 않아도 된다. 다만 역할을 나누어 trace에 기록하면 해당 역할 계약을 따른다.
- 역할은 에이전트에 영구적으로 고정하지 않고 작업 단위로 배정한다.
- 역할 문서는 [`AGENTS.md`](../../AGENTS.md), [Harness baseline](../baseline/README.md), [승인 정책](../policies/approval-policy.md), [병렬 작업 정책](../policies/parallel-work-policy.md)의 범위와 권한을 확장하지 않는다.

## 역할 구성

| 역할 | 주 책임 | 기본 쓰기 권한 | 상세 계약 |
|---|---|---|---|
| Lead | 범위 해석, 역할·소유권 배정, 결과 통합, 최종 검증·보고 | 요청 범위 또는 배정한 파일 | [lead.md](lead.md) |
| Researcher | 승인된 범위의 읽기 전용 조사와 근거 수집 | 없음 | [researcher.md](researcher.md) |
| Implementer | 배정받은 파일의 변경과 자체 검증 | 배정받은 파일 | [implementer.md](implementer.md) |
| Reviewer | 결함, 회귀, 누락과 운영 위험의 독립 검토 | 없음 | [reviewer.md](reviewer.md) |
| Verifier | 정의된 evaluator 실행과 PASS/FAIL/BLOCKED 판정 | 없음 | [verifier.md](verifier.md) |

## 역할 배정 계약

Lead가 역할을 배정할 때 다음 항목을 명시한다.

- 목표와 성공 조건
- 실행 역할과 담당 범위
- 읽어야 할 입력과 근거
- 수정 가능 파일 또는 디렉터리와 파일 소유권
- 금지 행동과 승인 필요 행동
- 실행할 evaluator 또는 검증 기준
- 일시 중단하고 Lead에게 에스컬레이션해야 하는 조건
- 작업을 재개할 수 있는 결정과 입력
- 역할별 반환 형식

입력 일부가 없어도 안전하게 조사할 수 있으면 역할 담당자는 확인된 범위까지만 진행하고 누락을 반환한다. 누락이 변경 범위, 외부 상태, 비용, 보안 또는 완료 판정을 바꾸면 임의로 가정하지 않고 Lead에게 반환한다.

## 일시 중단과 재개

역할 담당자가 접근 제한, 범위 충돌, 미확정 결정 또는 예상하지 못한 변경을 발견해도 전체 작업을 즉시 종료하지 않는다. 안전하게 진행할 수 있는 범위까지만 수행한 뒤 해당 역할을 일시 중단하고 다음 상태 중 하나로 Lead에게 에스컬레이션한다.

| 상태 | 의미 |
|---|---|
| `NEEDS_LEAD_DECISION` | 현재 요청 범위 안에서 Lead의 재배정, 대체 방법 또는 계약 갱신이 필요함 |
| `NEEDS_USER_APPROVAL` | 범위 확대, 외부 상태, 비용, 보안 또는 파괴적 행동에 사용자 승인·결정이 필요함 |
| `BLOCKED` | Lead와 사용자 확인을 거쳐도 현재 조건에서 안전한 재개 경로가 없음 |
| `COMPLETED` | 배정받은 역할 범위와 반환 계약을 완료함 |

에스컬레이션에는 다음 내용을 포함한다.

- 현재까지 수행한 범위와 확인한 결과
- 접근할 수 없는 자료 또는 충돌한 조건
- 필요한 추가 접근, 결정 또는 파일 소유권
- 결과, 일정, 외부 상태와 위험에 미치는 영향
- 승인 없이 가능한 대체 방법
- 작업 재개에 필요한 Lead 또는 사용자 결정

Lead는 현재 사용자 요청과 policies 안에서 다음 방법을 우선 검토한다.

- 기존 자료 또는 안전한 대체 근거 제공
- Researcher에게 추가 읽기 전용 조사나 교차 검증 배정
- 역할 범위, 순서 또는 파일 소유권 재배정
- 허용된 대체 evaluator나 검증 방법 지정

이 방법으로 해결할 수 없고 사용자 권한이 필요한 경우에만 `NEEDS_USER_APPROVAL`로 사용자에게 확인한다. Lead가 역할 배정 계약에 결정, 추가 입력, 변경된 권한과 재개 조건을 명시하면 역할 담당자는 갱신된 계약으로 작업을 이어간다. Researcher는 추가 근거를 제공할 수 있지만 범위 확대, 승인, 파일 소유권 또는 작업 재개를 독자적으로 결정하지 않는다.

## 역할 겸임과 독립성

- 소규모 작업에서는 Lead가 Researcher, Implementer 또는 Verifier를 겸임할 수 있다.
- 하나의 에이전트가 여러 역할을 수행하면 수행 시점의 역할과 적용 권한을 구분해 trace에 기록한다.
- 자신이 작성한 변경을 Reviewer 역할로 독립 검토할 수 없다. 자체 검토는 Implementer의 검증으로만 기록한다.
- 강화 Harness의 멀티·서브에이전트 작업에서는 Implementer와 Reviewer를 분리한다.
- Reviewer와 Verifier는 변경 작성에 참여하지 않은 동일 에이전트가 겸임할 수 있다.
- 고위험 멀티·서브에이전트 작업에서는 Implementer, Reviewer, Verifier를 각각 분리한다.
- 필요한 독립성을 확보하지 못하면 독립 리뷰나 독립 검증을 완료했다고 판정하지 않고, 그 한계와 남은 위험을 Lead에게 반환한다.

역할을 전환해 수정 작업을 수행하려면 Lead가 새 역할과 파일 소유권을 먼저 배정한다. Reviewer나 Verifier가 발견한 문제를 직접 수정해야 하는 경우에도 자동으로 쓰기 권한이 생기지 않는다.

## 공통 반환 계약

모든 역할은 자신의 범위에 해당하는 다음 내용을 Lead에게 반환한다.

- 결론과 수행 범위
- 근거 파일·라인, 명령 또는 판단 근거
- 변경 파일과 파일 소유권 준수 여부
- 실행한 검증과 결과
- 검증하지 못한 항목과 남은 위험
- 현재 상태와 일시 중단·에스컬레이션 사유
- Lead가 결정·통합해야 할 사항과 재개 조건

역할별 문서는 이 공통 항목을 생략하지 않고 필요한 산출물을 추가한다. 민감정보, 운영 데이터 원문, 긴 명령 출력은 반환이나 trace에 복사하지 않는다.

## 완료와 최종 판정

각 역할의 완료는 배정받은 범위의 반환 계약을 충족했다는 뜻이다. 전체 작업의 완료를 의미하지 않는다. Lead만 통합된 결과, evaluator 결과, 미검증 항목과 승인 상태를 종합해 최종 완료 여부와 사용자 보고를 결정한다.

역할 문서를 추가하거나 이름을 바꾸면 상단 역할 구성 표의 링크도 함께 갱신한다. [`scripts/doctor.sh`](../../scripts/doctor.sh)는 실제 역할 문서와 README 색인의 일치 여부를 검사한다.
